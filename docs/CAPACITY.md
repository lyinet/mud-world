# 容量实测与扩容结论（W6）

> 本文件是**实测报告**，不是设计推演。所有数字都来自本仓库当前代码在开发机上的实测；
> 报告证据（`reports/capacity/raw-*.json`、`probe-*.json`）已入库，可用第 8 节命令复现；
> 运行日志 `*.log` 是本地临时产物，不入库（见 `.gitignore`）。

## 1. 结论摘要

| 问题 | 结论 |
|---|---|
| 单进程当前能安全承载多少并发席位 | **100 席**（`think=2s` 时读 P95 12ms、写动作 P95 241ms、CPU 55%） |
| 多少席开始劣化 | **>100 席**；150 席写动作 P95 已到 958ms，CPU 91% 无余量 |
| 单进程极限 | **≈150 席**（读仍快，但写请求排队，动作延迟进入秒级） |
| 能否单进程到 500 席 | **不能**。GIL 下每请求约 7ms CPU，单核上限 ≈140 req/s；500 席 `think=2s` 需要 500 req/s，至少 3.5 核 |
| 500 席怎么办 | **必须分区**，方案与代价见 [PARTITIONING.md](./PARTITIONING.md) |
| 无玩家世界确定性 | 红线保持：golden 最新基线（V6 两套）全部通过，逐字节一致 |
| `seq_gap` | 所有档位、所有轮次均为 **0**；SQLite 不是瓶颈 |
| 5 分钟稳定性（200 席） | 错误率 0%、`seq_gap` 0、不变量 PASS；但写动作 P95 4.97s，**RSS 未收敛**（70→160MB） |
| 磁盘增长 | 61 写/s 时 **0.062–0.108 MB/s ≈ 5.3–9.3 GB/天**，必须配归档/retention |

一句话：**150 席“够用”这个说法只在读接口成立；算上写动作，当前单进程的安全线是 100 席。500 席需要分区，不是调优能解决的。**

## 2. 测试口径

- 机器：开发机，10 核（共享），测试期间 `loadavg` 5.8–7.6，其它会话有负载 → 绝对数字偏悲观。
- 服务端：`PYTHONPATH=src python -m wsim.api --auth on --seed 42`，`XKX_AMBIENT=0`（关闭 NPC 自走，只测玩家流量）。
- 每档位**独立干净世界**（`runs/cap-<label>-<seats>`），避免多档位叠加污染。
- 负载：`tools/load_test.py --players N --duration 90 --think-time 2 --ramp-up 8`。
  每席位循环 = 1 次 `GET /api/player/state` + 1 次 `POST /api/player/action`，然后 sleep 2s。
  这是**读写混合口径**：每席位每轮固定贡献 1 读 + 1 写。
- 与 `OPS-RUNBOOK.md §6` 的 W5 旧表（150 席 `/api/state` P95 156ms）不可直接比较：
  那张表是**只读**负载（无写动作争锁），本轮把写动作计入后，同一档位读延迟会随写队列一起抬升。
  下面的表全部是读写混合口径。
- 300 席档位：通过 `tools/capacity_overrides/sitecustomize.py` 把 `MAX_REGION_PLAYERS` 临时抬到 300
  （**仅测量口径**；出厂上限仍是 200 席 / 60000 赋能，未改动）。
- 指标来源：`tools/load_test.py` 的报告（含新增的 `status_codes` / `request_counts_by_endpoint` /
  `seq_gap_max` / `db_growth_mb_per_s` / `rss_growth_mb`）。
- 归因：`tools/capacity_probe.py` 在进程内替换 `session.lock`，量锁等待、持有时间、等待线程数、
  `WorldState.clone()` / `apply_effects` / `EventStore.append` 分段耗时。

### 瓶颈指认（基线，进程内探针）

| 席位 | 锁等待 P50 / P95 | 锁持有 P50 / P95 | 等待线程 max / P95 | 单线程读 | 单次写（含 clone） | clone 均值 |
|---|---|---|---|---|---|---|
| 50 | 0 / 65 ms | 4 / 13 ms | 48 / 16 | <1 ms | 5 ms | 3 ms |
| 100 | 1 / 108 ms | 6 / 18 ms | 96 / 16 | <1 ms | 9 ms | 5 ms |
| 150 | **135 / 845 ms** | 7 / 22 ms | **142 / 70** | <1 ms | 8 ms | 7 ms |
| 200 | **699 / 1534 ms** | 7 / 24 ms | **192 / 127** | <1 ms | 11 ms | 7 ms |

**第一个饱和点：全局写锁排队，不是 SQLite。**
- 读操作本身 <1ms，却要排队 135–699ms；150 席时 142 个线程同时等同一把锁。
- 锁持有 7ms，其中 `WorldState.clone()` 约 7ms（200 席），`EventStore.append` 仅 0.2–0.4ms。
- `seq_gap` 全程 0、DB 增长线性、无 5xx：排除 SQLite 与磁盘。
- 顺序：**① 全局锁把读也串行化 → ② 单核 GIL 限制总 CPU → ③ 每写整世界深拷贝抬高锁持有时间**。

## 4. 优化项与前后对比

### 4.1 读路径移出写锁（快照读）

改动：
- `src/wsim/api/session.py:396` 每线程读上下文；
- `src/wsim/api/session.py:491` `_read_snapshot()`：捕获 Writer 当前投影引用，锁外计算；
- `src/wsim/api/session.py:529-564` `status/quests/player_state` 改用快照；
- `src/wsim/api/session.py:505-527` 视图/任务排序缓存改为线程本地（弱引用，不钉住旧世界）。

安全性：Writer 只做 `self.state = trial` 原子替换，已提交状态不再原地修改；一次请求内所有字段来自
同一版本，不会撕裂读。

| 档位 | 基线 state P95 | 优化后 state P95 | 基线 CPU | 优化后 CPU |
|---|---|---|---|---|
| 50 | 19.7 ms | **3.5 ms** | 31.8% | 18.9% |
| 100 | 719 ms | **11.9 ms** | 81.9% | 55.4% |
| 150 | 1773 ms | **13.9 ms** | 95.6% | 91.0% |
| 200 | 2701 ms | **20.9 ms** | 106% | 100% |
| 300* | 6888 ms | **21.9 ms** | 118% | 118% |

读延迟改善 1–2 个数量级。但注意：**这只把等待从读转移到写**——写动作延迟并没有因此变好
（150 席时基线 161ms → 优化后 69ms 是第二项优化带来的，见 4.2）。

### 4.2 深拷贝改为 pickle 值拷贝

改动：`src/wsim/world/state.py:387-395`，`clone()` 从逐字段 `copy.deepcopy` 改为 pickle 往返。
200 席状态下实测 **6.1ms → 3.0ms**；状态是纯数据（dataclass/dict/list/元组/标量），
写入失败时旧投影仍不受影响；不可 pickle 的对象会直接报错而不是产生半拷贝别名。

| 档位 | clone 均值（前 → 后） | 写动作 P95（前 → 后，进程内） | 写吞吐（前 → 后） |
|---|---|---|---|
| 50 | 3 → 2 ms | 87 → 17 ms | 23.4 → 23.4/s（think 限制） |
| 100 | 5 → 3 ms | 135 → 241 ms（HTTP 口径含排队） | 39.9 → 45.8/s |
| 150 | 7 → 4 ms | 902 → 958 ms（HTTP 口径含排队） | 39.4 → 61.5/s |
| 200 | 7 → 4 ms | 1722 → 3069 ms（HTTP 口径含排队） | 36.4 → 61.4/s |
| 300* | 8 → 4 ms | 3250 → 7575 ms（HTTP 口径含排队） | 28.5 → 55.3/s |

说明：进程内写动作 P95 在 150 席是 433ms（优化后），上表 958ms 是 HTTP + 同步突发口径。
优化后 150 席写吞吐从 39/s 提到 61/s，但队列仍在 150 席时饱和。

### 4.3 红线验证

- `pytest tests/test_p3e_golden.py`：最新 golden（V6 两套）**通过**；其余 18 个是历史版本基线，按文件头说明显式 skip。
- 全量 `pytest -q`：除 2 个与本改动无关的既存失败外全部通过：

## 6. 200 席 5 分钟 soak（稳定性）

口径：`load_test.py --players 200 --duration 300 --think-time 2 --ramp-up 8 --sample-interval 5`
（同一服务端持续压 5 分钟，不是 90s 短跑）。原始数据 `reports/capacity/raw-opt2-soak-200.json`。

| 指标 | 结果 |
|---|---|
| 请求 | 24,226（`state` 11,813 + `action` 11,813 + 注册/登录/进入 600） |
| 吞吐 | 79.0 req/s；38.5 写/s；39.5 读/s |
| `/api/player/state` P50 / P95 / P99 | **7.2 / 52.1 / 184.9 ms**（5 分钟内比 90s 短跑差：20.9 → 52.1ms） |
| `/api/player/action` P50 / P95 / P99 | **3434 / 4974 / 6727 ms**（直接体现写队列稳态深度） |
| 错误率 | **0%**（24,225×200 + 1×429 容量拒绝；无 5xx、无 401） |
| `seq_gap` | **0**（55 个采样点全部为 0，事件 24,228 条连续） |
| 不变量 | PASS：钱包合计 delta=0、事件 seq 连续、`integrity_check=ok` |
| CPU | 均值 94.1%，峰值 228%（爬坡期多线程瞬时） |
| RSS | 基线 15.8 → 峰值 171.6 → 结束 169.1 MB；**前 60s 均值 69.8 → 末 60s 均值 160.3 MB** |
| SQLite | 4.5 → 23.1 MB，**0.062 MB/s ≈ 5.3 GB/天** |

结论（按实际情况写，不粉饰）：
- **错误率、`seq_gap`、不变量都干净**，说明 5 分钟内没有数据面故障。
- **RSS 在 5 分钟内没有收敛**：席位一次性分配约占 0.3MB/席，剥离后仍以约 0.1–0.15MB/s 缓慢上升。
  5 分钟不足以判定是否泄漏；同机 2 小时 soak（`reports/soak/soak-20261106-015816`）显示
  tokens/outbox/quests 类结构仍在增长（HEAD `116231a` 已封顶一部分），**需要 ≥2 小时复测才能下结论**。
  这里只如实记录：200 席 5 分钟内从 70MB 涨到 160MB。
- **写动作 P95 ~5s、吞吐只有 38.5 写/s**：200 席已经越过拐点，吞吐被延迟反压（200 席 / (2s think + ~3s 写延迟) ≈ 40 写/s），
  不是“能处理 61 写/s 只是慢一点”——是队列持续变长，属于过载。

## 7. 扩容判断

- **100 席以内**：可安全承载。读 P95 <12ms、写动作 P95 241ms、CPU 55%，留有余量。
- **100–150 席**：读接口仍健康，但写动作进入 1 秒级，体感明显变差；视为劣化区。
- **150 席以上**：单写者 + GIL 导致写队列线性增长；200 席写动作 P95 3.07s（90s 短跑）/ **4.97s（5 分钟稳态）**、300 席 7.57s。
- **500 席**：单进程不可达。即使把 clone 再优化到 0，每请求仍要 ~3ms CPU（HTTP/JSON/鉴权/视图），
  500 席需 ~500 req/s ≈ 1.5–2.5 核，超过单进程 GIL 上限。**需要分区（多进程/多写者）**，
  方案与代价见 [PARTITIONING.md](./PARTITIONING.md)。

没有实现 `150→500` 的单进程扩容；也没有为了“显得能干”而做未验证的优化。
未做的候选（因风险/收益不划算）：写时复制 clone（需要逐效果审计 44 个 op，红线风险高）、
读响应瘦身（会改 API 契约）。
