## 0. 结论

**判定：有条件可信。**

机制层是真的，验收层是虚的：

- **真的部分**：插件确实拿深拷贝、拒绝会整笔回滚；Effect 白名单在加载期生效；LOD 最小堆在 60 tick 窗口内确实只 decide 11 次；Provider 确实没有网络代码，离线必然降级到 Mock。

**开发方被点名美化的三项**：

1. **"越权 MCP 被拒"**：只在调用方如实声明低权限时成立。调用 `call(caller, permission, ...)` 的 `permission` 是入参，没有身份→权限映射；`reader_lowpriv` 自称 `admin_apply` 后拿到 `admin:2`，第三方 `mallory` 成功 apply（seq=3）。差的是整套身份认证，不是一条断言。

### 2.1 check 1：没有证明"零改码"

- 反向证据 1：临时内容副本只加动词元数据 `verify_brew`，跑 2 天 → `verbs_mismatch:content_only=verify_brew;engine_only=`。**动词不是零改码，必须写插件。**
- 反向证据 2：临时内容副本新增 NPC `verify_guest`（带 30 文）→ `money_supply_npc_total:35650!=35680`。`new_content.py npc --money` 不会同步经济总量数据。

### 2.2 check 2：隔离是真的，检查是弱的

独立恶意插件结果（`audit_evidence.json → plugins`）：

| 场景 | 结果 |
|---|---|
| `evil_mutate` 改 `stamina` | `PluginError: plugin_mutated_state`；真实 state 哈希不变 |
| Writer 提交同上 | `rejected:effect_invalid(plugin_mutated_state)`；事件 `effects=[]`；store 1→2 |
| `evil_undeclared` 返回未声明 `transfer` | `PluginError: undeclared_effect:transfer`；Writer 拒绝，rollback 完整 |
| `evil_partial` 先 transfer 再坏 debt_create | `rejected:effect_invalid(债务方无法映射账户: ghost_account)`；哈希前后一致；事件 `effects=[]` |

### 2.3 check 3：四种拒绝成立，但"越权拒绝"总体不成立

用户要求的四种拒绝，逐条有证据（`mcp_audit.jsonl`，14 条记录、7 条拒绝）：

但同一套代码允许：

```

  → {"token": "admin:2", "requester": "reader_lowpriv"}
gw.call("colleague", "admin_apply", "admin.approve", {"token": "admin:2"})
  → {"approved": true}
gw.call("mallory", "admin_apply", "admin.apply", {"token": "admin:2"})

```

`MCPGateway.call(caller, permission, method, params)` 第 71 行把 `permission` 当普通入参；第 125 行 `_require` 只检查字符串是否合法。`admin.apply` 也不校验 caller 是否为 requester/approver。**"双人"只是两个任意字符串。** 接 UI 后，任何前端都能自称 admin。

## 4. 六个怀疑点逐条

### 4.1 framework_check 五项是不是"空过" —— **部分成立**

五项确实都执行了，数字也大多是真的；但：
- check 1 不证明零改码，且检测不到 NPC 停摆；
- check 2 不测恶意插件；
- check 3 不测身份冒充；
- check 4 的核心断言是恒真式；
- check 5 复用 check 1。

它能证明"框架模块能跑通"，不能证明"世界被这些模块正确驱动"。

### 4.2 插件隔离是否只是弱哈希检查 —— **部分成立**

- 强：`copy.deepcopy(state)` 传给插件；真实 state 物理隔离。事务失败整笔回滚，事件只留一条 `effects=[]` 的 rejected 记录。
- 弱：哈希检查漏掉 `tick`、`locations`；"改动即拒绝"对这两个字段不成立。
- 白名单：加载期拒绝 `mint` 和未知原语；运行期拒绝未声明原语。

### 4.3 MCP 越权是否真的拒绝 —— **部分成立（四种指定场景成立；总体不成立）**

- read→propose、propose→admin、单人批准、伪造 token 四种都拒绝，且 14 条审计记录含 7 条拒绝，字段完整。
- 但"权限"由 caller 自报；自称 admin 即可完成 request→approve→apply 全链路；apply 也不要求 caller 是 approver。
- 审计只记录"你声称的权限"，记录 `caller=reader_lowpriv, permission=admin_apply` 反而是越权证据，而不是阻止越权。

### 4.4 LOD 是否真的不遍历全量 —— **部分成立**

- 60 tick 内确实只 decide 11 次、只取 11 次 state，唯一 NPC 11 个；逐 tick 调用也是 11 次，不是"遍历了但没调用"。
- 但 scheduler 是孤岛：主循环仍对全部 NPC 发 `system_plan`（30/天），`framework_check` 的 LOD 用的是合成 state_provider（stamina 固定 80），不是真实世界。
- "只唤醒 11/31"是调度器内部事实，不是整个模拟的事实。

### 4.5 新增内容是否污染 K1 分母与旧基线 —— **成立（这是最值得警惕的一项）**

## 5. 总判定

**有条件可信。**

可信的是"框架零件"：深拷贝隔离、事务回滚、Effect 白名单、最小堆调度、离线降级、内容 manifest 校验（错误带 `content/additions/npcs.yaml:23` 行号）都经得起独立验证。

不可信的是"验收结论"：五项 PASS 既不能证明零改码，也不能阻止越权，更不能发现 NPC 停摆。08:42 快照 641 条事件、310 条拒绝、NPC 零动作、`burned=0`，`framework_check` 仍报五项全 PASS；08:48 最新快照 608/4210=14.4% 拒绝，同样 PASS。这是最直接的"空过"证据。

### 接真实模型与 UI 前必须先补的三件事

1. **身份与权限（阻断级）**
   - 删除 `call(caller, permission, ...)` 里的 caller 自报权限；改为服务端身份→权限映射。
   - token 绑定 requester + approver；`admin.apply` 校验调用者就是批准人；token 不可顺序猜测。
   - 审计记录要能回答"谁以什么凭证做了什么"，而不只是"他声称自己是谁"。

2. **把验收门禁做成真门禁（阻断级）**
   - 记录 `src/` 哈希基线或引入 git，check 1 用 diff 证明零改码，不再硬编码 `ming_chabo` 等 id。
   - 增加最低活跃度断言：`rejected/events < 1%`、每日 NPC 动作数 > 0、`burned > 0`、K1 分母与内容包目标数一致；否则当前停摆树必须 FAIL。
   - check 5 改为从 `events.sqlite` 独立重算，不再复用 check 1 的 summary。
   - check 4 删掉 `process_count == len(wakes)` 恒真断言，改用独立 reasoner/provider 计数器。

3. **接线与文档（上线前）**
   - 把 LODScheduler 接进 `headless.py`，用真实 state provider 替换合成的 `stamina=80`；否则"11/31 唤醒"只是孤岛演示。
   - 把 `ProviderClient → FallbackReasoner → decide` 接到 NPC 决策路径；当前 headless 完全不使用它。
   - 在 `ARCHITECTURE.md` 标注"LOD/MCP/Provider 当前均未接主循环"，并冻结交付快照后再出验收数字。
