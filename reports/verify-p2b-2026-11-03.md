## 6. K1 68/91 的算术复现 —— 不成立（作为可比数字）

三个可执行事实：

```
P1 存档 rev72d：        68/90 = 75.56%，content_hash = b639ab91…，13 类 verb
提交 5f09de1 重跑 72d： 41/91 = 45.05%，content_hash = 83bcd141…， 9 类 verb
交付 42f4914 重跑 72d： 70/91 = 76.92%，content_hash = 7acace8f…，17 类 verb
```

- **没有任何提交能重跑出 P1 的 68/90**。`5f09de1` 号称基线，但跑出 41/91，且内容哈希与 P1 存档不同。
- 用当前冻结代码回放 P1 存档：

```
$ .venv/bin/python tools/replay.py --run runs/rev72d
WARN content_hash changed: run=b639ab91a999 replay=7acace8f2337
events=19322
replayed=d03c7052…  stored=e4254a50…  MISMATCH
```

- 只有用 `5f09de1` 的代码才能回放 P1 存档（`MATCH`，`e4254a50…`）：

```
$ .venv/bin/python /tmp/p2b-5f09de1/tools/replay.py --run runs/rev72d
replayed=e4254a50…  stored=e4254a50…  MATCH
```

**所以：**
1. **旧基线永久丢失**（在没有外部备份的前提下）：既不能由提交再生，也不能在交付树上回放；只能在 `5f09de1` 的代码上回放。
   这是"版本锁定"的基线，不是"可复现"的基线。
2. **所有"对比 P1"的结论都受影响**：内容哈希三版各不相同（`b639ab91` / `83bcd141` / `7acace8f`），
   任何 P1→P2 的数字差都同时混入了**内容变更 + 代码变更 + 口径变更**，无法归因。
   以后若要论证"改进了"，必须固定同一内容包与同一签名 spec，跑两个代码版本，而不是引用 `rev72d` 存档。
3. **报告里的 68/91 是合成数**：分子 68 来自 90 目标世界，分母 91 来自新内容包。它没有对应的任何一次真实运行。

额外发现（直接削弱"K1 改善"）：

```
P1：68 − 23(一次性) = 45，分母 90 − 23 = 67 → 67.16%
P2：70 − 25(一次性) = 45，分母 91 − 25 = 66 → 68.18%
```

**两边剔除一次性后的分子完全相同（45）。** 总 K1 的 +2 也全部来自一次性目标（`build_shop` 12 + `gain_status` 12 + `found_sect` 1）。
所谓"K1 从 74.73% 提升到 76.92%"既包含合成分母，又主要来自分母 67→66 的变化，**不宜作为能力提升的证据**。

| 复核项 | 判定 |

| 1. 冻结真实性 | **成立（附条件）**：交付代码确实冻结在 `42f4914`；但复核结束时工作区因外部进程多了未跟踪 `ui/`，"干净"不是持续状态 |

**总判定：有条件可信。** 交付快照"世界内"的数字可以采信；"对比 P1"与"K1 改善"的叙事不可以采信，

分子来自另一个世界（90 目标），分母来自新世界（91 目标）；
